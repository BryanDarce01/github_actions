# Cancelación y omisión (Skipping) en GitHub Actions

## 1. Cancelar vs. hacer Skip

Aunque pueden parecer similares, son conceptos diferentes:

-   **Cancelar:** detener una ejecución que ya comenzó.
-   **Skip (omitir):** evitar que un workflow, job o step se ejecute
    porque no cumple ciertas condiciones.

Podemos actuar en distintos niveles: workflow, job o step.

## 2. Cancelar manualmente un workflow

Desde la interfaz de GitHub:

1.  Entrar al repositorio.
2.  Abrir la pestaña **Actions**.
3.  Seleccionar la ejecución (*workflow run*) que está en curso.
4.  Elegir **Cancel workflow**.

También se puede cancelar desde GitHub CLI:

``` bash
gh run cancel RUN_ID
```

`RUN_ID` es el identificador de la ejecución que queremos cancelar.

## 3. Omitir un workflow con `[skip ci]`

GitHub permite incluir instrucciones especiales en el mensaje del commit
para omitir workflows activados por `push` o `pull_request`.

Por ejemplo:

``` bash
git commit -m "Actualiza documentación [skip ci]"
```

GitHub reconoce estas instrucciones:

``` text
[skip ci]
[ci skip]
[no ci]
[skip actions]
[actions skip]
```

| Expresión | Significado |
|---|---|
| `[skip ci]` | Omitir la integración continua (Continuous Integration). |
| `[ci skip]` | Exactamente lo mismo, pero con el orden invertido. |
| `[no ci]` | No ejecutar la integración continua. |
| `[skip actions]` | Omitir las ejecuciones de GitHub Actions. |
| `[actions skip]` | Lo mismo, con el orden invertido. |

También se puede utilizar el trailer:

``` text
Actualiza documentación

skip-checks: true
```

### Importante

Estas instrucciones se aplican a los eventos `push` y `pull_request`; no
son una forma general de omitir workflows activados por cualquier
evento.

Además, cuando se omite un workflow de esta manera, los checks asociados
pueden quedar en estado **Pending**. Si una regla de protección de ramas
exige que esos checks terminen correctamente, esto puede impedir el
merge del Pull Request.

### ¿Qué significa CI?

**CI significa Continuous Integration (Integración Continua).**

Es una práctica de desarrollo en la que, cada vez que se incorporan cambios al repositorio, se ejecutan automáticamente procesos como:
- Tests para comprobar que el código funciona.
- Linting para revisar la calidad y el estilo del código.
- Builds para comprobar que la aplicación se puede construir.
- Validaciones para detectar errores.
Por eso, cuando escribimos [skip ci], estamos indicando que queremos omitir las ejecuciones de integración continua asociadas a ese commit.

## 4. Omitir un workflow mediante filtros

Podemos evitar que un workflow comience si el evento no coincide con los
filtros configurados:

``` yaml
name: Main workflow

on:
  push:
    branches:
      - main
```

Este workflow solamente se activa para pushes a `main`.

También podemos utilizar `paths` o `paths-ignore` para limitarlo según
los archivos modificados.

Esto no es una cancelación: el workflow no llega a iniciarse porque el
evento no cumple las condiciones.

## 5. Omitir un job mediante `if`

La propiedad `if` permite ejecutar un job solamente cuando una condición
se cumple.

``` yaml
name: Example

on: push

jobs:
  test:
    runs-on: ubuntu-latest
    if: false
    steps:
      - run: echo "Este job no se ejecutará"

  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Este job sí se ejecutará"
```

En este ejemplo, el workflow comienza, pero el job `test` se omite
porque su condición es `false`.

También podemos evaluar información del contexto:

``` yaml
if: github.ref == 'refs/heads/main'
```

En este caso, el job se ejecutará solamente cuando la referencia sea la
rama `main`.

## 6. Omitir un step mediante `if`

`if` también puede utilizarse en un step:

``` yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Primer paso
        run: echo "Este paso se ejecuta"

      - name: Paso omitido
        if: false
        run: echo "Este paso no se ejecuta"

      - name: Último paso
        run: echo "Este paso también se ejecuta"
```

El job continúa ejecutándose; únicamente se omite el step cuya condición
es falsa.

## 7. Cancelar ejecuciones anteriores con `concurrency`

Podemos configurar GitHub para cancelar una ejecución anterior cuando
llega otra ejecución del mismo grupo.

``` yaml
name: Build

on:
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Construyendo aplicación"
```

### ¿Qué hace cada propiedad?

-   `concurrency`: configura la concurrencia de las ejecuciones.
-   `group`: define el grupo al que pertenece una ejecución.
-   `cancel-in-progress: true`: permite cancelar ejecuciones en curso
    del mismo grupo cuando llega una nueva.

En el ejemplo, el grupo se construye con el nombre del workflow y la
referencia de Git. Así, las ejecuciones del mismo workflow y de la misma
rama comparten grupo.

Esto resulta útil cuando hacemos varios pushes seguidos y queremos
evitar que se sigan ejecutando builds de versiones anteriores.

## 8. ¿Un job fallido cancela automáticamente todo el workflow?

No necesariamente. Es importante distinguir estos estados:

-   **Failure:** un job o step terminó con error.
-   **Skipped:** un job o step no se ejecutó porque fue omitido o porque
    no se cumplieron sus condiciones.
-   **Cancelled:** una ejecución o parte de ella fue cancelada.

Si un job falla, los jobs que dependan de él mediante `needs`
normalmente se omiten, porque sus dependencias no se completaron
correctamente. Sin embargo, otros jobs independientes pueden continuar.

Ejemplo:

``` yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: exit 1

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: echo "Normalmente se omitirá porque test falló"

  report:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Este job es independiente"
```

Aquí `test` falla, `build` normalmente se omite por depender de `test`,
pero `report` puede ejecutarse porque no depende de él.

Para ejecutar un job incluso si una dependencia falló o fue omitida, se
pueden utilizar condiciones como `always()`, teniendo cuidado de definir
correctamente qué resultados queremos aceptar.

**Idea clave:** un fallo no es lo mismo que una cancelación. GitHub
puede omitir jobs dependientes después de un fallo, pero eso no
significa que haya cancelado automáticamente todo el workflow.

## 9. Resumen

  -----------------------------------------------------------------------
  Mecanismo                           Resultado
  ----------------------------------- -----------------------------------
  Cancelar desde Actions              Detiene manualmente una ejecución
                                      en curso.

  - `gh run cancel`: Cancela una ejecución desde la
                                      terminal.

  - `[skip ci]`: Omite workflows activados por `push` o `pull_request`.

  - `branches` / `paths`: Evita iniciar el workflow si no se cumplen los filtros.

  - `if` en un job: Omite un job completo.

  - `if` en un step: Omite un step específico.

  - `concurrency`: Permite cancelar ejecuciones anteriores del mismo grupo.

  - `needs` después de un fallo: Normalmente omite los jobs que dependen del job fallido.

  -----------------------------------------------------------------------
