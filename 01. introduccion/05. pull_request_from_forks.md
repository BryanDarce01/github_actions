# Pull Requests desde Forks y aprobación de workflows

## 1. ¿Qué sucede cuando alguien externo crea un Pull Request?

En GitHub, una persona puede contribuir a un repositorio sin ser
colaboradora directa. Una forma común de hacerlo es:

1.  La persona crea un **fork** del repositorio original.
2.  Trabaja en su propia copia.
3.  Sube sus cambios a una rama de su fork.
4.  Abre un Pull Request hacia el repositorio original.

El Pull Request permite proponer cambios al repositorio original sin
tener permisos para escribir directamente en él.

## 2. ¿Por qué GitHub puede solicitar aprobación antes de ejecutar el workflow?

Un Pull Request desde un fork puede contener código que el repositorio
original no controla.

Si GitHub ejecutara automáticamente ese código en un runner con acceso a
secretos o permisos elevados, podría existir un riesgo de seguridad.

Por eso, GitHub puede requerir que una persona con permisos adecuados
apruebe la ejecución de workflows provenientes de ciertos colaboradores
externos.

En repositorios públicos, la configuración predeterminada normalmente
requiere aprobación para colaboradores que contribuyen por primera vez,
pero el alcance depende de la configuración del repositorio.

## 3. Configuración de aprobación

La configuración se encuentra en:

**Repository → Settings → Actions → General → Approval for running fork
pull request workflows from contributors**

Las opciones disponibles permiten establecer a quién se le solicita
aprobación, por ejemplo:

-   Colaboradores nuevos en GitHub que contribuyen por primera vez.
-   Todos los colaboradores que contribuyen por primera vez.
-   Todos los colaboradores externos.

Los nombres exactos y las opciones disponibles pueden variar según el
tipo de repositorio y la configuración de GitHub.

## 4. ¿Quién puede aprobar?

No necesariamente tiene que ser el dueño del repositorio. La aprobación
puede realizarla una persona que tenga los permisos requeridos para
administrar o ejecutar workflows en ese repositorio, normalmente alguien
con permisos de escritura o superiores, según la configuración.

## 5. Medidas de seguridad para workflows desde forks

En general, los workflows disparados por `pull_request` desde forks
tienen restricciones importantes:

-   No reciben los secretos del repositorio, salvo excepciones
    específicas de GitHub como el `GITHUB_TOKEN`.
-   El `GITHUB_TOKEN` se limita normalmente a permisos de solo lectura
    para estos casos.
-   La aprobación de la ejecución permite que el workflow corra; no
    significa que el Pull Request haya sido aprobado para merge.

Estas restricciones reducen el riesgo de que código no confiable acceda
a recursos sensibles.

## 6. Aprobación del workflow no es aprobación del Pull Request

Son dos decisiones distintas:

-   **Aprobar la ejecución:** autorizar que GitHub Actions ejecute el
    workflow asociado al Pull Request.
-   **Aprobar el Pull Request:** revisar los cambios y decidir si pueden
    integrarse en la rama destino.

Un mantenedor puede aprobar la ejecución del workflow y después rechazar
los cambios del Pull Request.

**Idea clave:** GitHub puede pedir aprobación antes de ejecutar
workflows de Pull Requests provenientes de forks para proteger el
repositorio frente a código no confiable.
