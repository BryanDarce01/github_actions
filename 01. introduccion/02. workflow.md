# 1. ¿Qué es un workflow?

Un **workflow** es un proceso automatizado definido mediante un archivo YAML.

Este archivo establece:

- Qué eventos pueden desencadenar el workflow.
- Qué jobs se ejecutarán.
- Cómo se relacionan los jobs entre sí.
- Qué pasos se ejecutarán dentro de cada job.

Los workflows se almacenan normalmente dentro del directorio:

```text
.github/
└── workflows/
    ├── test.yml
    └── deploy.yml
```

Cada archivo YAML dentro de `workflows` puede definir un workflow independiente.

## 1.1. Estructura de un workflow

Un workflow contiene principalmente:

```yaml
name: Mi workflow

on:
  push:

jobs:
  mi_job:
    runs-on: ubuntu-latest
    steps:
      - name: Mi step
        run: echo "Hola"
```

| Elemento | Descripción |
|---|---|
| `name` | Nombre del workflow. |
| `on` | Eventos que desencadenan el workflow. |
| `jobs` | Trabajos que componen el workflow. |
| `runs-on` | Runner donde se ejecutará el job. |
| `steps` | Pasos que ejecutará el job. |
| `run` | Ejecuta un comando de terminal. |
| `uses` | Utiliza una acción existente. |

# 2. Events / Triggers

Un **event** es un acontecimiento que sucede en GitHub y que puede desencadenar la ejecución de un workflow.

Los eventos se definen mediante la propiedad `on`.

Por ejemplo:

```yaml
on: push
```

Este workflow se desencadena cuando ocurre un evento `push` que cumple con las condiciones configuradas.

## 2.1. Eventos relacionados con el repositorio

| Evento | Descripción |
|---|---|
| `push` | Se envían cambios al repositorio. |
| `pull_request` | Ocurre una actividad relacionada con un Pull Request. |
| `create` | Se crea una rama o etiqueta. |
| `fork` | Se crea un fork del repositorio. |
| `issues` | Ocurre una actividad relacionada con un Issue. |
| `issue_comment` | Se crea, edita o elimina un comentario en un Issue o Pull Request. |
| `watch` | Alguien marca el repositorio con una estrella. |
| `discussion` | Ocurre una actividad relacionada con Discussions. |

## 2.2. Otros eventos

| Evento | Descripción |
|---|---|
| `workflow_dispatch` | Permite ejecutar un workflow manualmente. |
| `repository_dispatch` | Permite desencadenar un workflow mediante una solicitud a la API de GitHub. |
| `schedule` | Permite ejecutar un workflow mediante una programación cron. |
| `workflow_call` | Permite que un workflow sea llamado por otro workflow. |

## 2.3. Múltiples eventos en un workflow

Un workflow puede tener uno o varios eventos.

Si queremos que se ejecute tanto con `push` como con `pull_request`, podemos escribir:

```yaml
name: Mi workflow

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Mostrar mensaje
        run: echo "Workflow ejecutado"
```

También podemos utilizar una lista:

```yaml
on: [push, pull_request, workflow_dispatch]
```

Ambas formas permiten definir múltiples eventos.

En este ejemplo, el workflow puede ejecutarse cuando:

- Se realiza un `push`.
- Ocurre una actividad de `pull_request`.
- Se ejecuta manualmente mediante `workflow_dispatch`.

## 2.4. Filtrar eventos

Podemos especificar cuándo debe activarse un evento.

Por ejemplo, ejecutar el workflow solamente cuando se realice un `push` a la rama `main`:

```yaml
on:
  push:
    branches:
      - main
```

También podemos combinar eventos y filtros:

```yaml
on:
  push:
    branches: [main]

  pull_request:
    branches: [main]
```

Esto permite ejecutar el workflow ante los eventos configurados, pero solamente cuando cumplen las condiciones de las ramas indicadas.

# 3. Jobs

Un **job** es un conjunto de steps que se ejecutan dentro de un mismo runner.

Los jobs permiten dividir un workflow en diferentes trabajos.

Por ejemplo, un workflow podría tener:

- Un job para ejecutar pruebas.
- Un job para construir la aplicación.
- Un job para desplegar la aplicación.

Cada job tiene un identificador único dentro del workflow.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Ejecutar pruebas
        run: echo "Ejecutando pruebas"

  build:
    runs-on: ubuntu-latest
    steps:
      - name: Construir aplicación
        run: echo "Construyendo aplicación"
```

En este ejemplo tenemos dos jobs:

- `test`
- `build`

## 3.1. Jobs en paralelo

Por defecto, los jobs de un workflow pueden ejecutarse en paralelo si no existe una dependencia entre ellos.

Por ejemplo:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Ejecutar pruebas
        run: echo "Ejecutando pruebas"

  build:
    runs-on: ubuntu-latest
    steps:
      - name: Construir aplicación
        run: echo "Construyendo aplicación"
```

GitHub Actions puede ejecutar ambos jobs al mismo tiempo.

Esto permite reducir el tiempo total de ejecución del workflow.

## 3.2. Jobs en cadena mediante `needs`

Si un job depende de otro, podemos utilizar la propiedad `needs`.

`needs` indica que un job debe esperar a que otro job termine correctamente antes de ejecutarse.

Ejemplo:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Ejecutar pruebas
        run: echo "Pruebas completadas"

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - name: Construir aplicación
        run: echo "Construcción completada"

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Desplegar aplicación
        run: echo "Despliegue completado"
```

La ejecución será:

```text
test
  ↓
build
  ↓
deploy
```

En este caso:

1. Se ejecuta `test`.
2. Cuando `test` termina correctamente, se ejecuta `build`.
3. Cuando `build` termina correctamente, se ejecuta `deploy`.

## 3.3. Dependencias múltiples

Un job puede depender de varios jobs utilizando una lista:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Pruebas"

  lint:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Validación de código"

  build:
    needs: [test, lint]
    runs-on: ubuntu-latest
    steps:
      - run: echo "Construcción"
```

En este caso:

```text
      test ────┐
               ├──→ build
      lint ────┘
```

`test` y `lint` pueden ejecutarse en paralelo.

`build` espera a que ambos terminen correctamente.

# 4. Runners

Un **runner** es una máquina o entorno que ejecuta los jobs de un workflow.

Los runners proporcionan el entorno donde se ejecutan los comandos y las acciones.

Cada job necesita un runner.

## 4.1. GitHub-hosted runners

GitHub proporciona runners predefinidos con diferentes sistemas operativos.

Por ejemplo:

```yaml
runs-on: ubuntu-latest
```

Otros ejemplos:

```yaml
runs-on: windows-latest
```

```yaml
runs-on: macos-latest
```

Estos runners son administrados por GitHub.

## 4.2. Self-hosted runners

También podemos crear nuestros propios runners.

Estos son máquinas que nosotros administramos y configuramos para ejecutar los jobs.

Pueden ser útiles cuando necesitamos:

- Un entorno específico.
- Hardware especial.
- Acceso a recursos internos.
- Configuraciones personalizadas.

# 5. Steps

Un **step** es una tarea individual que se ejecuta dentro de un job.

Los steps se ejecutan secuencialmente, uno después del otro.

Cada step puede:

- Ejecutar comandos de terminal mediante `run`.
- Utilizar una acción mediante `uses`.

Ejemplo:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Descargar repositorio
        uses: actions/checkout@v4

      - name: Mostrar mensaje
        run: echo "Repositorio descargado"

      - name: Mostrar directorio
        run: ls
```

En este ejemplo tenemos tres steps.

El segundo step se ejecuta después del primero y el tercero después del segundo.

---

# 6. Actions

Una **action** es una unidad reutilizable de código que permite realizar una tarea dentro de un workflow.

Las actions permiten reutilizar funcionalidades sin tener que escribir todos los comandos manualmente.

Se utilizan mediante la propiedad `uses`.

Por ejemplo:

```yaml
steps:
  - name: Descargar repositorio
    uses: actions/checkout@v4
```

`actions/checkout` es una action que permite descargar el repositorio en el runner para poder trabajar con su código.

También podemos ejecutar comandos de terminal directamente:

```yaml
steps:
  - name: Instalar dependencias
    run: npm install

  - name: Ejecutar pruebas
    run: npm test
```

Por lo tanto, un step puede utilizar una action o ejecutar comandos mediante `run`.

---

# 7. Workflow Execution

Un workflow se ejecuta cuando ocurre alguno de los eventos definidos en su configuración y se cumplen las condiciones establecidas.

Durante la ejecución, GitHub Actions proporciona información sobre:

- El estado de los jobs.
- El estado de los steps.
- Los logs de ejecución.
- Los errores que ocurren.
- La duración de los procesos.

Podemos consultar esta información desde la pestaña **Actions** del repositorio.

# 8. GitHub Context y expresiones `${{ }}`

GitHub Actions proporciona diferentes contextos que contienen información sobre el workflow y su ejecución.

Uno de los más importantes es el contexto `github`.

Para acceder a esta información se utilizan expresiones:

```yaml
${{ }}
```

Estas expresiones permiten obtener valores dinámicos durante la ejecución del workflow.

## 8.1. Obtener metadata del workflow

Por ejemplo:

```yaml
${{ github.repository }}
```

Devuelve el nombre del repositorio en formato:

```text
usuario/repositorio
```

Otros valores importantes:

| Expresión | Descripción |
|---|---|
| `${{ github.repository }}` | Nombre completo del repositorio. |
| `${{ github.actor }}` | Usuario que inició el workflow. |
| `${{ github.event_name }}` | Nombre del evento que desencadenó el workflow. |
| `${{ github.ref }}` | Referencia que desencadenó el workflow. |
| `${{ github.sha }}` | SHA del commit asociado al evento. |
| `${{ github.workflow }}` | Nombre del workflow. |
| `${{ github.run_id }}` | Identificador de la ejecución del workflow. |

## 8.2. Ejemplo

```yaml
name: Información del workflow

on:
  push:

jobs:
  info:
    runs-on: ubuntu-latest

    steps:
      - name: Mostrar metadata
        run: |
          echo "Repositorio: ${{ github.repository }}"
          echo "Usuario: ${{ github.actor }}"
          echo "Evento: ${{ github.event_name }}"
          echo "Workflow: ${{ github.workflow }}"
```

Aquí utilizamos `${{ }}` para insertar valores del contexto `github` dentro de los comandos.

Por ejemplo, si el repositorio es `BryanDarce01/github-actions`, el comando ejecutado podría ser:

```bash
echo "Repositorio: BryanDarce01/github-actions"
```

**Importante:** `${{ }}` es la sintaxis de expresiones de GitHub Actions. No es una sintaxis propia de YAML ni de Bash.

# 9. Ejemplo completo de un workflow

Este ejemplo combina los principales conceptos aprendidos:

```yaml
name: CI Pipeline

on:
  push:
    branches: [main]

  pull_request:
    branches: [main]

  workflow_dispatch:

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Descargar repositorio
        uses: actions/checkout@v4

      - name: Mostrar información
        run: |
          echo "Repositorio: ${{ github.repository }}"
          echo "Evento: ${{ github.event_name }}"

      - name: Ejecutar pruebas
        run: echo "Ejecutando pruebas"

  build:
    needs: test
    runs-on: ubuntu-latest

    steps:
      - name: Construir aplicación
        run: echo "Construyendo aplicación"

  deploy:
    needs: build
    runs-on: ubuntu-latest

    steps:
      - name: Desplegar aplicación
        run: echo "Desplegando aplicación"
```

## ¿Qué sucede en este workflow?

1. Se activa mediante `push`, `pull_request` o `workflow_dispatch`.
2. Se ejecuta el job `test`.
3. Se descarga el repositorio.
4. Se muestra metadata del workflow.
5. Se ejecutan las pruebas.
6. Cuando `test` termina correctamente, se ejecuta `build`.
7. Cuando `build` termina correctamente, se ejecuta `deploy`.

La estructura de ejecución es:

```text
Event
  ↓
Workflow
  ↓
test
  ↓
build
  ↓
deploy
```

# Resumen

| Concepto | Función |
|---|---|
| YAML | Formato utilizado para definir la configuración del workflow. |
| Workflow | Proceso automatizado definido en un archivo YAML. |
| Event | Acontecimiento que puede desencadenar un workflow. |
| Job | Conjunto de steps que se ejecutan en un runner. |
| Runner | Máquina o entorno donde se ejecuta un job. |
| Step | Tarea individual dentro de un job. |
| Action | Código reutilizable que realiza una tarea. |
| `on` | Define los eventos que desencadenan el workflow. |
| `needs` | Define dependencias entre jobs. |
| `${{ }}` | Permite utilizar expresiones y obtener valores dinámicos. |
| `github` | Contexto que contiene metadata sobre el workflow y su ejecución. |

**Idea principal:** un workflow define qué automatizar, los eventos determinan cuándo ejecutarlo, los jobs organizan el trabajo, los runners proporcionan el entorno, los steps realizan las tareas y las actions permiten reutilizar funcionalidades.
